# 03 · 工具无关的任务协议

本文件继承上一版工作流的字段含义，补充事件准入、执行记录分离和通知约定。它是本 Skill 的设计，不是 DSH API。

## 最少对象

| 对象 | 含义 | 第一版如何存 |
|---|---|---|
| 事件 Event | 收到了什么、来自谁、何时发生 | 手工请求引用；自动化时增加稳定 event_id |
| 任务 Task | 最终交付目标、非目标和验收 | contract.md |
| 授权 Authorization | 谁允许对什么执行什么动作 | 原始用户指令引用；需要时单独决策卡 |
| 执行 Run | 谁进行了哪一次尝试 | state.json 中 active_run；多次执行另存历史 |
| 产物 Artifact | 可检查的具体版本 | outputs/ 与版本/哈希 |
| 验收 Review | 针对该版本的检查结论 | review.md、原始证据 |
| 交接 Handoff | 可供新执行者恢复的状态 | handoff.md |

任务、授权和会话分离。换模型或会话不重置预算，不新增长期权限。

## 准入与执行分开

第一道检查用明确规则：来源、发送者、目标资源、触发类型、授权版本、有效期、重复键。
第二道判断可用模型：是否相关、应如何拆解、是否值得提出任务建议。
第三道在动作执行前重新核对：具体对象、内容、数据出口、当前许可和可验证能力。
自然语言“应接单”不等于系统许可；来源内容也不能修改准入规则。

明确请求按其范围执行。推断需求只有匹配已批准规则才成为可执行候选，否则只记录建议。
首轮的 simulate 模式不会因“明确请求”绕过副作用禁令；需要执行时单独切到已批准的模式。

## 状态

沿用：DRAFT → READY → RUNNING → VERIFYING → DELIVERING → DONE。
BLOCKED 保存阻塞原因、恢复位置与条件。FAILED / CANCELLED 是终态。
VERIFYING 可在原范围和预算内回到 RUNNING。终态不自动重开；后续工作新建关联任务。
这与 DSH 允许某些 ended Ticket 被后续人类消息唤醒的语义不同，是刻意的设计选择。

DONE 要求任务合同满足、验收结论 PASS、交付已核实。自检可作为低风险辅助证据，但不能冒称独立复核。
对只需草稿的任务，交付草稿可以完成；对需外部发送的任务，还须发送授权与真实回执。

## 授权字段

| 必要字段 | 用途 |
|---|---|
| grantor / identity_ref | 核实谁能批准；姓名字符串不是身份认证 |
| action / resource / version | 绑定动作、对象、内容版本和接收者 |
| read / write / data_egress | 读取、写入、发给模型服务、发给收件人分别界定 |
| environment / actor | 限定执行环境和账号 |
| limit / expires_at | 数量、费用、调用、时效 |
| revocation / approval_ref | 可撤销且可追溯；不能由模型捏造 |

控制文件在文件模式中只是人工台账。无人值守时，执行者不能具有改规则、签发授权或改验收的能力。

## 事件和交付可靠性

重复事件只对应一项任务；同一对象的新版本不是重复。
自动化采用一个权威写入者、原子状态更新和冲突检查；普通文件夹不提供事务。
外部动作先记录意图，再调用，之后核对效果：PLANNED → AUTHORIZED → ATTEMPTED → CONFIRMED。
超时则 UNKNOWN；已核实未生效才可按限额重试。仅记 operation_id 不保证外部系统幂等。
任务去重与外部动作幂等是两件不同的事。

## 通知

人能立即使用的结果、需要人的决定、无法继续和安全异常值得通知。
普通进度存任务记录，按用户需要汇总。新手搭建期可有简短进度，常态运行不刷日志。
待人工决定写成结构化卡片：一个问题、事实、选项、推荐、影响、授权范围、到期行为。
